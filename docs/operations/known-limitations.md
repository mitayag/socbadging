# Known Limitations

- Phase 8 credentials are signed Open Badges 3.0-aligned records. Credentials issued before Phase 8 remain available as legacy unsigned records and are not presented as cryptographically verified. The system is not Open Badges certified; production HTTPS activation, official 1EdTech conformance submission, and written approval remain external milestones.
- Student password recovery is implemented through single-use email recovery links (30-minute expiry). Administrators can reset eligible active student passwords directly or send a reset link; Faculty can do the same only for students actively enrolled in classes they own. Direct resets force a password change at next sign-in, invalidate sessions, and invalidate outstanding reset tokens. Authenticated users can also change their own password from Account Settings, and Administrators can reset Faculty access with a temporary password.
- Students can activate a portal account through an Administrator invitation and access private wallet, notification, profile, and download features. Students who have not activated an account can still use the public verification link received by email or shared by Faculty.
- Brevo webhook status processing is implemented for delivered, deferred, hard/soft bounce, blocked, invalid-email, and complaint events. Events are HMAC-authenticated, size-limited, idempotent, correlated to deliveries, and protected against out-of-order regression. Permanent hard bounces, spam complaints, invalid recipients, and provider-confirmed blocks create durable recipient suppression enforced by the worker, retries, resends, student email, and recovered queue jobs. Suppression is cleared only by an audited Administrator procedure; complaint suppression requires explicit acknowledgement. `SENT` means the SMTP provider accepted the message, not confirmed inbox delivery. Production deliverability, sender reputation, provider webhook registration, and provider policies remain deployment responsibilities. See [Recipient Suppression Policy](recipient-suppression.md).
- PDF credentials are human-readable summaries only; the signed JSON-LD credential remains authoritative.
- Email is asynchronous and depends on a separately running worker and configured SMTP provider. Mailpit is the default local transport. Brevo mode requires `EMAIL_DELIVERY_MODE=brevo`, an explicit `EMAIL_RECIPIENT_POLICY` (`staging` or `production`), `EXTERNAL_EMAIL_ENABLED=true`, port 587 with STARTTLS, and valid SMTP credentials. Staging uses an exact-recipient allowlist; production permits only recipients tied to system-issued issuance/student envelopes. Controlled acceptance mode can further restrict sends. Issuance/revocation remains successful during an outage; delivery can remain Pending, Retry Scheduled, or Failed until recovery or Administrator retry. Retry backoff and bounded attempts are implemented.
- Mailpit is a development inbox, not a production mail provider. Production sender-domain verification, SPF, DKIM, DMARC, Brevo sender approval, provider webhook registration, deliverability, and sender reputation remain deployment responsibilities. Automated tests retain Mailpit as the default transport and must not send external email without explicit authorization.
- Local Docker-volume media storage is the MVP default. S3-compatible object storage is future P1 work.
- Evidence attachments and basic issuance analytics remain unimplemented P1 items.
- HTTPS termination/proxy deployment is documented but external to the application Compose stack. Local `APP_URL`, `ISSUER_URL`, and `SIGNING_KEY_ID` use `http://127.0.0.1`; production issuance and verification URLs must be replaced through the key/issuer configuration plan without rewriting historical signed credentials.
- The public status list is published and externally verifiable locally after the Stage 5C.1 repair. If an existing immutable credential ever references an unrepairable publication, it must be documented and handled through controlled reissuance rather than silently rewriting the signed payload. See [Status-List Architecture](../conformance/status-list-architecture.md).
- Production dependency advisories remain after the Next.js security upgrade; see [the dependency security baseline](dependency-security.md).
- Local screenshots under `docs/screenshots/` may contain disposable E2E or local fixture names, emails, and credential data. Treat them as internal artifacts and redact or exclude them from external releases.
